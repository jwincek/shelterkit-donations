# Changelog

All notable changes to Shelter Donations (formerly Starter Shelter Donations) will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

## [2.0.0] - 2026-07-05

### Changed
- **Renamed the plugin's public identity to `shelter-donations`** ("Shelter Donations") in
  preparation for the first WordPress.org release, joining the `shelter-*` plugin family
  (shelter-pet-sync, shelter-events-wrapper). This is a **breaking release** for existing
  installs — follow `migration-scripts/MIGRATION-2.0.0.md` when upgrading a live site.
  - Text domain: `starter-shelter` → `shelter-donations` (plugin header, all gettext calls,
    translation template renamed to `languages/shelter-donations.pot`).
  - Main plugin file: `starter-shelter.php` → `shelter-donations.php` (existing installs must
    reactivate; the plugin directory must be renamed to `shelter-donations/` to match the slug).
  - Block namespace: `starter-shelter/*` → `shelter-donations/*` (12 blocks), including the
    Interactivity API store namespaces and block-binding sources. **Stored content that uses
    these blocks must be migrated** with `wp search-replace` — see the migration guide.
  - Editor bootstrap global: `window.starterShelterBlocks` → `window.shelterDonationsBlocks`.
  - WP-CLI command: `wp starter-shelter validate` → `wp shelter-donations validate`.
  - Display name, log prefixes, and metadata (composer, PHPCS ruleset, Plugin/Author URI)
    updated to the new identity; Author is now "VCPA Humane Society", crediting the
    organization the plugin was originally built for.
- **Unchanged on purpose** (no data migration needed): the `Starter_Shelter\` PHP namespace and
  `STARTER_SHELTER_*` constants (internal-only), all `starter_shelter_*` hook/filter/cron names,
  all `sd_*` option/meta keys and post types, and WooCommerce product/order data.
- Dist packaging: `.distignore` now also excludes dev artifacts (`phpcs.xml.dist`,
  `.editorconfig`, `.wp-env.json`, PHPUnit caches, `AUDIT-*.md`, `migration-scripts/`).

## [1.2.0] - 2026-06-23

### Added
- **My Account → Annual Statement** now produces a real, printable tax receipt. The "Print / Save as PDF" button opens a standalone, print-optimized contribution statement (no theme/account chrome) that auto-opens the browser print dialog — so members get a PDF via their browser with no server-side PDF dependency. It itemizes the year's donations, memorials, and memberships with a grand total, includes the organization details (from the WooCommerce store settings) and the donor's name/address, and carries a deductibility note that's filterable (`starter_shelter_receipt_tax_note`) so a site can add its EIN / 501(c)(3) language. The donor is resolved from the session, so a member only ever prints their own statement. (Previously the Print button just reloaded the full account page.)
- **My Account → Donor Dashboard** now has an editable **Contact Details** form (name, phone, mailing address), pre-filled from the donor record. Saving posts through the nonce-verified PRG handler and the owner-scoped `shelter-donors/update-profile` + `shelter-donors/update-address` abilities — completing the self-service set (previously the account area was entirely read-only).
- **My Account → My Memberships** now lets members manage their memberships directly: an **auto-renew toggle** and a **Cancel membership** action (with confirm) on each active membership, plus the existing Renew link (now pointing at the configured membership page instead of the site home). Both post through the same nonce-verified PRG handler, which checks the membership belongs to the current user's donor before acting; cancellation runs through the `shelter-memberships/cancel` ability. Cancelling clears the term so the member also drops off the public Members Wall.
- **My Account → My Memberships** now lets a member control their public recognition: a "List me on the public Members Wall" preference (opt-out model) that members can toggle themselves. This is the self-service counterpart to the Members Wall — previously a member had no way to opt out. Posts back via a nonce-verified PRG handler that resolves the current user's own donor (so a user can only change their own record), sets `is_anonymous` across their memberships, and the recognition-wall ability honors it immediately. Logic lives in WooCommerce-free `My_Account::set_recognition_preference()` / `is_listed_publicly()` (integration-tested).
- New **Members Wall** block (`starter-shelter/members-wall`) — a static (SSR, no-build) tiered recognition wall of active members who haven't opted out, grouped into membership-level sections ordered highest-first. Business members show their approved logo (toggleable) and link to their website; individuals show their display name. Inspector controls: group-by-tier, show-logos, columns, max-items. Backed by a new public read ability `shelter-memberships/recognition-wall` (active + not anonymous; resolves business name or donor display name; sorts by tier amount then name). **Opt-out model:** members appear unless `is_anonymous` is set — so placing this block publishes the names/logos of all current active members. Renders nothing on the front end when no members qualify.
- New **Business Member Slideshow** block (`starter-shelter/business-slideshow`) — a no-build, Interactivity-API (WP 6.9/7.0) carousel of active business members with an approved logo. All eligible members are server-rendered into a CSS-transform track and rotated client-side (no fetch/loading state); off-screen slides are `inert` for correct tab order and screen-reader behavior. Autoplay pauses on hover/focus, respects `prefers-reduced-motion`, and offers prev/next + play-pause + dot controls; an explicit pause isn't overridden by hover. Each logo links to the member's website (`target="_blank" rel="noopener noreferrer"`) when set; the business-name caption is an optional block attribute (plus autoplay toggle, interval, and max-items in the inspector). Backed by a new public read ability `shelter-memberships/business-directory` (active + `membership_type=business` + `logo_status=approved` + resolvable logo, sorted by business name) and a new `logo_url` computed field on `sd_membership` (mirrors the memorial `photo_url`). Renders nothing on the front end when no members qualify.
- Memorial wall now has a **Dedication filter** dropdown (All Dedications / In Memory Of / In Honor Of) alongside the existing Type (person/pet) filter — the two axes are independent and compose. Mirrors the type filter end-to-end: `shelter-memorials/list` gained a `dedication` input (`all`/`memory`/`honor`), `list_memorials()` adds a `dedication_type` query constraint, and the block render + Interactivity store thread it through the `memorial-dedication` URL param (server re-render on change, bookmarkable, carried through pagination + load-more, and reset by Clear). No new block attribute — the control defaults to "all".
- PHPUnit test suites (PHPUnit 9.6 — the version the WordPress core test framework supports) with CI jobs across the PHP 8.1–8.3 matrix. The manifest validator checks structural contracts statically; these tests cover runtime behavior it can't see.
  - **Unit suite** (`composer test`, `unit-tests` job): pure functions, no WordPress bootstrap — the memorial/dedication helpers (`normalize_memorial_type`, `normalize_dedication_type`, `get_memorial_type_label`, `get_dedication_type_label`) and `Donor_Lookup::sanitize_display_name`. The few WP functions these call (`__`, `wp_strip_all_tags`) are stubbed in `tests/bootstrap.php`; runs in ~15ms with no database.
  - **Integration suite** (`composer test:integration`, `integration-tests` job): boots a real WordPress 7.0 + MySQL (no WooCommerce — the code under test is WC-free and the plugin self-guards) and exercises the create/list data flows across all three entities: memorials (donor display-name preference, dedication persistence + filter, anonymous path, hydrator computed labels, CSV Dedication column), donations (allocation default + override, anonymous, donor lifetime-giving accumulation, pre-resolved donor_id, campaign attach, list-by-allocation), and memberships (tier/type/amount, +1-year term, tier-amount fallback, business fields, lifetime giving, and renewal extending an active term + recording the order). Also covers the SQL aggregation reports — `shelter-donations/get-stats` (totals, count, distinct-donor count, average, by-allocation breakdown, campaign scoping), `shelter-reports/dashboard-stats` (cross-entity roll-up of donations / active+new memberships / memorials / donor totals), and the type-aware `shelter-reports/campaign-progress` (donation-drive raised vs membership-drive member-count, goal/progress/remaining math, tier filtering, the 100%-cap, and is_active) — the hand-written SUM/COUNT queries the Query builder can't express and where a silent miscount would hide. Backed by `bin/install-wp-tests.sh`, a curl-based (no-svn) installer for the WP test library; see `tests/README.md`.
  - Tooling: `phpunit/phpunit ^9.6` in `require-dev`; `config.platform.php` pinned to 8.1.0 and `composer.lock` committed for reproducible CI; the CI `integration-tests` job runs against a MySQL service container.
- `dedication_type` (In Memory Of / In Honor Of) is now surfaced on the display layers, not just stored. Three places: the **memorial wall** block shows it as an eyebrow label above each honoree name (both the SSR fallback and the Interactivity client template); the admin **Memorials list table** shows it as a sub-line under the Type (Person/Pet) badge; and the **memorial CSV export** gains a "Dedication" column. Driven by a new `dedication_type_label` computed field on the `sd_memorial` manifest (mirroring `memorial_type_label`), backed by two new helpers `Helpers\normalize_dedication_type()` and `Helpers\get_dedication_type_label()`. Legacy rows with an empty `_sd_dedication_type` read as "In Memory Of" (the field default).
- Memorial admin edit screen now exposes the memorial-form's two orthogonal axes — **Dedication** (In Memory Of / In Honor Of) and **Honoree Type** (Person / Pet) — as separate fields in the (classic) meta box, instead of the single conflated `human/pet/honor` select. Rendered declaratively from the manifest. (An alternative block-editor sidebar UX exists in `assets/js/memorial-panel.js` but is parked/un-enqueued — see that file's header for why and how to revive it.)
- New first-class `dedication_type` memorial field (`memory` / `honor`, default `memory`, `show_in_rest`). Wired end-to-end: manifest field + `shelter-memorials/create` input + `create` ability persists `_sd_dedication_type` + product input-mapping reads `_sd_dedication_type` from cart/order item meta. This **closes a data-loss gap**: the memorial-form already collected the customer's In Memory / In Honor choice and the cart handler saved it to order-item meta, but it was never mapped into the memorial post — so the wall couldn't distinguish a memorial from an honorarium. New memorials (customer-submitted and admin-entered) now persist it.
- New `shelter-reports/campaigns-progress` (plural) batch ability returns campaign-progress entries for many campaigns in 2-3 SQL queries: one GROUP BY for donation totals, one GROUP BY for membership counts, plus a `update_termmeta_cache` prime. Per-campaign tier_filter falls back to a focused count (rare path). Reports → Campaigns tab now uses this single call instead of N invocations of the singular `shelter-reports/campaign-progress`; the singular version stays as-is for one-off lookups (e.g., campaign-card).
- `shelter-reports/campaign-report` ability is now type-aware. Donation drives return `{ progress: { total_raised, ... }, donations: [...] }` (unchanged shape); membership drives return `{ progress: { member_count, percent_of_goal, remaining }, memberships: [...] }`. The per-campaign CSV export on the Reports → Campaigns tab now produces a membership-shaped CSV (Member / Email / Tier / Type / Start / End / Status / Amount) for membership drives, and an enriched donation CSV (Date / Donor / Email / Amount / Allocation) for donation drives. The summary block at the top of the file now also shows campaign type and uses "Joined" instead of "Raised" for membership drives.
- Reports campaign filter now also scopes the stats cards and donation-trend chart (previously only per-record tables filtered). Three additional abilities gained a `campaign_id` input property and accompanying SQL: `shelter-donations/get-stats`, `shelter-reports/dashboard-stats`, `shelter-reports/donation-trend`. Each adds an `INNER JOIN wp_term_relationships + wp_term_taxonomy` only when `campaign_id > 0`, then constrains `tt.term_id = %d`. Donor totals (lifetime / new-in-period) deliberately stay unfiltered — donors aren't directly campaign-tagged; we'd need a transitive join through donations/memberships which changes the metric's meaning. Notice copy under the filter now reflects the new scope.
- Reports tabs (Donations, Memberships, Memorials) now have a Campaign filter dropdown. Picking a campaign filters the per-record table to that campaign's conversions; stats cards remain period-wide for comparison and the page surfaces a notice clarifying the scope. The CSV Export carries the filter through (filename suffix `-campaign-{id}`). To support this, `shelter-memberships/list` and `shelter-memorials/list` gained a `campaign_id` input property and the callbacks now thread it into `Query::for(...)->whereInTaxonomy('sd_campaign', ...)`. `shelter-donations/list` already supported the param.
- `membership-form` editor inspector now exposes a Campaign picker, mirroring `donation-form`. Behaves identically: admin-set value wins over URL auto-tagging, no campaign locking when the picker is unset.
- Auto-tag donations and memberships to a campaign via `?campaign={id}` in the page URL. New helper `Helpers\resolve_campaign_id_from_request()` reads the query var, validates it against `sd_campaign`, and returns the term ID (or 0). `donation-form` and `membership-form` block renderers now use it as a fallback when no `campaignId` block attribute is set, so a click through campaign-card lands on the form page and the resulting donation/membership is attached to the originating campaign — the existing cart→order→ability `_sd_campaign_id` plumbing carries it through. `membership-form` gained a `campaignId` attribute (it had none), state/context wiring, "Supporting: {name}" badge, and `campaign_id` is now appended to its cart-submission formData.
- New `donation_page` and `membership_page` settings (Settings → General → Pages). `campaign-card` uses them to build the CTA target — donation drives link to the donation page, membership drives link to the membership page, both with `?campaign={id}` appended. Same settings replace the hardcoded `home_url('/donate/')` in `donor-dashboard/render.php` and `class-my-account.php::render_no_donor_message()`. When a page is unset the button is hidden rather than emitting a broken link, so admins notice the missing CTA and configure it. Two new helpers: `Helpers\get_donation_page_url()` and `Helpers\get_membership_page_url()`.
- `campaign-card` block now has an editor inspector: campaign picker (sourced from `window.starterShelterBlocks.campaigns`), display-option toggles (goal / raised-or-joined / donors / end date / donate button), and a progress-bar color swatch. Server-side render in the canvas previews the selected campaign.
- `campaign-card` button label is now type-aware: "Donate Now" on donation drives, "Join Now" on membership drives.
- `campaign-card` editor preview now loads the block's style.css (via new `editorStyle` declaration in block.json), so the progress bar and stats render the same in the editor as on the frontend.

- **My Account → My Candles** — a new sub-section listing the memorials a member has lit a candle for (a personal "memorial garden"), linking to each. Candles are a permanent tribute (no expiry); candles lit while logged out merge into the member's account on login (`merge_anonymous_candles_on_login`). User-scoped, so it works even for a logged-in visitor without a donor profile.
- **Full data backup (CSV ZIP)** on the Import / Export page — a "Download full backup" button bundles the donors / donations / memberships / memorials CSVs plus a README into one ZIP (`admin_post_sd_export_all`). Intended before uninstalling with delete-data enabled. (A hard export gate inside `uninstall.php` isn't possible — plugin deletion runs server-side with no way to stream a download — so the backup lives in the plugin UI.) `Csv_Exporter::build_csv()`/`build_archive()` expose the CSV content for bundling.
- **"Delete all data on uninstall" setting + `uninstall.php`.** Data is **preserved by default** — donation/membership/memorial/donor records are financial and tribute data, so uninstall never deletes them unless an admin explicitly opts in (a new Data Management setting, off by default, that warns to back up first). When enabled, the purge removes plugin-owned data only — the four CPTs + meta, the three taxonomies' terms, the activity-log table, `sd_*` options + the settings blob, candle user-meta, and transients — and always keeps WooCommerce products (referenced by orders) and the media library. Cleanup lives in `includes/uninstall-cleanup.php` (core/`$wpdb` only, network-aware).
- **WooCommerce HPOS compatibility** is now declared (`custom_order_tables` via `FeaturesUtil::declare_compatibility` on `before_woocommerce_init`). The plugin already read/wrote orders through the `WC_Order` API and branched on `OrderUtil` for its one raw order query, so it was HPOS-safe — declaring it stops WooCommerce flagging the plugin as incompatible and unblocks admins enabling HPOS.
- **WooCommerce-enabled test lane** (`composer test:wc`, `wc-tests` CI job): boots real WooCommerce and installs its tables (`bin/install-woocommerce.sh`), then exercises the order pipeline against the live WC runtime — the cart→order-item-meta **write** half (`save_cart_item_to_order`), the order→entity **read** half driven by a real status transition (which also satisfies the create abilities' `internal` permission), the no-double-process guard, and checkout-field save. Complements the WC-free integration suite.
- Backup **restore now round-trips campaign associations and logo/photo references.** Memberships and memorials gained a "Campaign" export column (donations already had one); on import the campaign is relinked by **name** (find-or-create the `sd_campaign` term) since term/post IDs change on restore. Memberships export/import a "Logo Attachment ID" and memorials a "Photo ID"; same-site restore relinks because the media library is preserved. Still **not** auto-restored: campaign goals/end-dates, candle counts, the activity log, and settings (documented in the backup README and the Import/Export UI).
- Memorial admin edit screen now exposes the **Family Mailing Address** and **send-physical-card** fields. The memorial form already collected them (and they have canonical flat storage read by the family-notification email), but the admin meta box omitted them, so an admin couldn't see or set them.

### Changed
- `My_Account::get_current_donor_id()` is now memoized per request (a non-persistent object-cache group). It runs an uncached `sd_donor` meta query and is called on every account page by the menu filter, the sub-nav, and each rendered section; the lookup body moved to `lookup_donor_id()`.
- My Account donor area is consolidated under a single **"My Giving"** menu item instead of five separate top-level account-menu entries (Donor Dashboard, Giving History, My Memberships, My Memorials, Annual Statement). The sub-sections now live in an in-page **sub-navigation** (tab bar) rendered on each donor page with the current section marked active, and "My Giving" stays highlighted in the WooCommerce account menu across all of them. Declutters the account menu; all endpoints remain registered and directly linkable.
- My Account endpoints are now real, overridable template files under `templates/myaccount/` (`donor-dashboard`, `giving-history`, `my-memberships`, `my-memorials`, `annual-statement`) instead of a ~400-line inline `switch` in `My_Account`. `render_template()` already preferred a theme override (`yourtheme/starter-shelter/myaccount/<name>.php`) then the plugin file; the dead inline fallback (`render_inline_template`) is removed. Markup is unchanged — themes can now customize the donor account UI without touching the plugin. (Each template runs in the plugin's WooCommerce namespace; overrides should keep the `namespace`/`use` header or use fully qualified function names.)
- Reports → Campaigns tab rebuilt on the type-aware `shelter-reports/campaign-progress` ability. New columns: Type (donation drive / membership drive pill), Goal (formatted per type — `$X` vs `Y members`), Progress ("$3,200 / $5,000 (64%)" or "75 / 100 members (75%)" with a fill bar), Ends (formatted end date), Status (Active / Ended pill), Actions. Replaces the previous table that hard-coded `_sd_goal` + a custom `get_campaign_raised()` helper (now removed) and surfaced `$campaign->count` mislabeled as "Donations" — that count was actually all-type post attachments. The tab now also displays a small note that it shows lifetime progress, since the page-level period selector doesn't apply per-campaign.
- `List_Columns` column configuration is now built lazily on first access instead of during plugin bootstrap, so `__()` calls no longer run before the `init` hook.
- `validate_item_meta()` return type relaxed from `true|WP_Error` to `bool|WP_Error`; the `true` literal type requires PHP 8.2+ and the plugin still declares an 8.1 floor.
- `campaign-card` block.json: removed `"ancestor": []` (empty array meant "no valid ancestors", hiding the block from the inserter even though it was registered). Added `"editorScript": "file:./edit.js"`.
- `campaign-card` donate button no longer carries `wp-element-button`, so themes stop overriding the configured `progressBarColor`. Added `box-sizing: border-box` to the card and descendants to prevent the full-width button overflowing the card (root cause: `width: 100%` + `padding: 0.875rem 1.5rem` under default `content-box`).

### Fixed
- My Account membership CTAs no longer link to the site home. The "Rejoin" (past membership) and "Become a Member" (no memberships) buttons now use the configured membership page (`Helpers\get_membership_page_url()`) and are hidden when no page is set — matching the campaign-card behavior of not emitting a broken link. The Giving History empty state gained a "Make a Donation" CTA (to the configured donation page) instead of a dead end.
- Object/array entity fields (e.g. donor `address`, `communication_preferences`) now hydrate correctly. `Entity_Hydrator` reads all meta in one bulk `get_post_meta( $id )` call, which returns PHP-serialized strings, but the array caster only ran `json_decode` — so every object field hydrated to `[]` (the donor address showed empty in My Account, computed `formatted_address` was blank, etc.). The caster now `maybe_unserialize`s first, falling back to JSON. Surfaced while building the My Account profile editor.
- The `owner_or_admin` ability permission now resolves ownership from an entity post id (`membership_id` / `memorial_id` / `donation_id`) via the post's donor, not only from a `donor_id`/`user_id` in the input. Previously an owner-scoped ability whose input is an entity id — e.g. `shelter-memberships/cancel` (input `membership_id`) — could never pass for a non-admin, so members couldn't self-cancel; admin still always passes.
- Membership `is_anonymous` is now persisted and hydrated. It was accepted in the membership ability/checkout schema (a shared field) but `create()` never wrote `_sd_is_anonymous` and the entity didn't declare it, so it was a read-with-no-writer — a member could never actually opt out. Now declared on the `sd_membership` entity (mirrors `sd_memorial`) and written by `create()`, so the public Members Wall can honor it.
- Memorial wall paged pagination is now consistent after client-side filtering. Two issues: the "Page X of Y" label was static server-rendered text (no binding), so it kept showing the unfiltered total (e.g. "Page 1 of 4" with 2 results) — it's now bound to live state. And the nav's `hidden` binding never took effect because `.sd-pagination--paged { display: flex }` overrode the `[hidden]` attribute, so the (correctly disabled) pager stayed on screen for single-page result sets; added a `.sd-pagination[hidden] { display: none }` rule. The nav is also now rendered whenever pagination is enabled (with the correct initial `hidden` state) rather than only when the initial set spans >1 page, so broadening a shared filtered URL can reveal it.
- Memorial wall loading state now stays visible for the whole request instead of clearing after ~1s while the old grid lingers. Filtering, search, and paged pagination now fetch results from the Abilities REST endpoint and replace the grid client-side (the same path "Load More" uses) rather than going through the Interactivity Router, whose `navigate()` resolved a beat before the swapped content painted — decoupling `isLoading` from the actual fetch. The URL is still kept in sync via `history.pushState` (a `popstate` listener reloads on back/forward so the rendered filters match the URL). This also fixes a latent bug in that REST call: it used `POST` to `…/shelter-memorials%2Flist/run`, but the read-only list ability requires **GET** with `input[...]` query params and a literal slash in the route — so the previous call (and Load More) returned 404/405. The REST base + nonce now come from the block context instead of a `wpApiSettings` global that isn't enqueued on the frontend.
- Memorial wall **"In Memory Of" dedication filter** now returns legacy memorials whose `_sd_dedication_type` was never written. Those rows display as "In Memory Of" (the normalize-on-read default) but the filter used a strict `_sd_dedication_type = 'memory'` equality, so they were excluded — making the filter look like it only worked for "In Honor Of" (which always has an explicit value). New `Query::whereDefaulted()` matches the value OR a missing/empty meta when the value is the implicit default; `list_memorials()` and the wall's SSR fallback use it for the dedication filter.
- Memorial wall now gives visible feedback while a filter/search/pagination is applying: the results count announces "Updating…" (it's an `aria-live` region, so screen readers hear it too), the grid sets `aria-busy`, and the filter controls are disabled with a wait cursor for the brief navigation. (The grid already dimmed with a spinner overlay; this makes the in-flight state unmistakable and prevents racing filter changes.)
- `shelter-donations/create` and `shelter-memberships/create` no longer emit a PHP 8 "Undefined array key" warning on the pre-resolved `donor_id` path (importers/sync). Both built the post title from `$input['donor_name'] ?? $input['donor_email']`, but that path supplies neither; the title now falls back to the donor record's title via `get_the_title( $donor_id )`. Surfaced by the new integration tests.
- Memorial donor display name now reflects the name entered on the tribute form. `create` set the memorial's denormalized `_sd_donor_display_name` from the resolved donor record's `_sd_display_name`, but `get_or_create_donor` doesn't overwrite an existing donor's display name — so a returning billing email showed the stored donor name instead of what the giver typed for that tribute. Now prefers the supplied `donor_name` (sanitized the same way the donor record is), falling back to the donor record only when no name was supplied.
- Per-campaign CSV export filename no longer embeds the page-level period selector's default value ("month"). The Campaigns tab is inherently lifetime + per-campaign — period doesn't apply. Filenames are now `shelter-campaign-{id}-{date}.csv` instead of `shelter-campaign-month-campaign-{id}-{date}.csv`.
- `shelter-reports/campaign-report` was reading `get_term_meta( $campaign_id, 'goal', true )` instead of the prefixed `_sd_goal` — the goal field was silently null for every campaign report, leaving `percent_of_goal` and `remaining` null in every CSV summary block. Now reads the canonical key (matching `campaign_progress` and the `Campaign_Admin` term-meta writer).
- `List_Columns` row layout no longer scrambles after Quick Edit. `register_columns()` and `register_sortable()` called `get_current_screen()` to disambiguate post type, but that global is null during `wp_ajax_inline_save()` — the filter then fell through to WP's default columns (`cb`, `title`, `date`), and the AJAX-returned row HTML didn't match the 8-cell table on the page. Filters now capture `$post_type` in a closure at registration time, removing the screen lookup entirely.
- Resolved "Translation loading was triggered too early" notice from `List_Columns::init()` running on `plugins_loaded` (same root cause as the 1.1.1 `Checkout_Fields` fix).
- WC Blocks mini-cart now refreshes after a form submit without requiring a page reload. The plugin was firing only `wc-blocks_added_to_cart` (the success event), but WC's mini-cart frontend uses a two-phase lazy-load — only `wc-blocks_adding_to_cart` is wired up initially, and the success listener isn't registered until the bundle finishes loading. Now firing both events (`adding_to_cart` before the fetch, `added_to_cart` on success with explicit `detail.preserveCartData: false` so the mini-cart refetches via the WC Store API).
- CI: `php -l` matrix step ran `find ... | grep -v 'No syntax errors'`, which exits non-zero on success — the job was reporting a clean codebase as a failure. Switched to `xargs -n1 php -l` so the step actually validates 8.1–8.3 compatibility.
- CI: added `phpcs.xml` (PHPCompatibilityWP ruleset, `testVersion=8.1-`); the `PHPCS Lint` job had been exiting 2 (usage error) every run because no config file was present.
- My Account **Annual Statement** year selector no longer disagrees with the rendered statement. The default was the prior (completed) tax year, but the dropdown only lists years that have contributions — so on a site whose gifts are all in the current year, the selector showed one year while the body rendered another ("$0.00") and the member's real totals were hidden. The default now falls back to the most recent year with data, and the resolved year is always present in the selector.
- **Order processing is guarded against concurrent double-processing.** The processed-flag check was check-then-set, so duplicate gateway webhooks — or a webhook racing an admin status change in a separate request — could each create a full set of donation/membership/memorial records. Processing now runs under a per-order MySQL advisory lock (`GET_LOCK`) with a fresh, HPOS-aware in-lock re-check of the processed flag.
- The **memorial create ability now assigns its campaign term** (`wp_set_object_terms`). Donations and memberships already did; memorials accepted `campaign_id` in the input schema but never attached the term, so a memorial could not belong to a campaign at all. Surfaced by the backup round-trip tests.
- **Block accessibility.** The Business Slideshow slide-picker used an invalid ARIA pattern — `role="tablist"` with `aria-selected` on plain `<button>`s and no tabs/tabpanels/`aria-controls` (and `aria-selected` is invalid on a button). It's now a labelled `role="group"` using `aria-current` for the active slide (consistent with the carousel's own roles). Members Wall tier sections are now labelled by their heading (`aria-labelledby`).

### Security
- **CSV / formula injection** neutralized across all exports (reports, entity exports, the import error/template files). A user-controlled cell beginning with `=`, `+`, `-`, `@`, tab, or CR (e.g. a donor or campaign name like `=HYPERLINK("//evil","x")`) is prefixed with a single quote so it can't execute when an admin opens the file in Excel/Sheets; genuine numbers are untouched. New `Helpers\esc_csv_field()` / `fputcsv_safe()` route every `fputcsv()` call.
- **Anonymous-donor privacy.** The public Business Directory now honors the recognition opt-out (`is_anonymous`) like the Members Wall already did — an opted-out business is no longer exposed there. And the public memorial-wall search no longer matches the donor's name, so a visitor can't confirm an anonymous gift by searching the giver's name; search targets the honoree (the public subject) only. Donors still find their own (incl. anonymous) memorials privately via My Account.
- **Memorial candle anti-abuse is now enforced.** `has_anonymous_candle()` — the documented per-IP guard — was defined but never called, so an anonymous visitor could clear the `sd_candles` cookie to re-increment a memorial's candle count without bound (throttled only to 1 per 2s). The server-side IP-hash transient is now authoritative for anonymous toggles; the cookie is a display hint only.
- Removed a dangling `wp_ajax_sd_quick_stats` registration that pointed at a non-existent handler (would fatal if invoked) — found during an AJAX / `admin_post` authorization audit that otherwise confirmed every state-changing handler is both nonce- and capability-guarded.
